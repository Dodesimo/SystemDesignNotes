
- Networking Essentials:
  - Built on OSI Model
  - Application Layer, Presentation Layer, Session Layer, Transform Layer, Network Layer, Data Link Layer, Physical Layer
  - Network Layer (3): IP protocol, break data up into packets, handle packet forwarding and provide best effort delivery.
  - Transport Layer (4): TCP, QUIC, UDP: end-to-end communication services, layer such as reliability, ordering, flow control.
  - Application Layer (7): DNS, HTTP, Websockets, RTC, build on top of TCP, UDP to provide a layer of abstraction for different types of data with web applications.
  - What happens on a simple web request:
    - DNS: convert a human-readable domain name into IP address.
    - Client initiates TCP connection with server: syn, syn-ack, ack
    - When a connection is established, the client sends a GET request to the server to request a web page.
    - The server processes the request, retrieves the requested web page, and prepares HTTP response.
    - Server sends the HTTP response back to the client, including the requested web page content.
    - TCP teardown: client sends a FIN to server to terminate connection, FIN gets acknowledged with ACK, server sends FIN packet to the client to terminate its side of the connection, ACK acknowledges this.
    - This connection between client and server is a state that both client and server maintain.
      - Unless we do keep-alive or HTTP/2 multiplexing, we repeat this for every request (significant overhead).
- Network Layer:
  - IP protocol, responsible for routing and addressing. IPs are assigned through a DHCP server when boot up.
- Transport Layer:
  - Transport layer: end-to-end communication between applications, give us guarantees about packet order.
  - TCP, UDP, QUIC.
    - UDP: User Datagram Protocol: simpler, connectionless service, no guarantees of ordering, delivery, duplicate protection.
      - Benefits: connectionless, no guarantee of delivery, no ordering, lower latency.
      - Useful when speed more important than reliability: live video streaming, online gaming, DNS lookups.
    - TCP:
      - Reliable, ordered, error-checked delivery of data.
      - Establish connection with a three way handshake.
      - Maintains a connection throughout the communication session, stateful connection.
      - Recipients of messages acknowledge their receipt and if not, retransmit message till acknowledged.
      - Benefits:
        - Connection oriented, reliable delivery, flow control, congestion control.
        - Ideal where data integrity is deep.
    - When to choose what over what?
      - UDP: when low latency critical, some data loss is predictable, handling high-volume telemetry or logs, don’t need to support web browsers.
- HTTP/HTTPS:
  - Built on top of transport layer protocols, specify how applications communicate.
  - HTTP:
    - Clients send requests to servers, servers respond with requested data.
    - Stateless: each request is independent, server doesn’t need to maintain information about previous requests.
    - Request methods, status codes, headers (meta data about request or response), body (actual contents)
    - Get (idempotent), request data, post, send data, put, update data, patch partially update data, delete, delete data (idempotent)
  - Status codes:
    - 200 OK, 201 created (new resource created), 302 found (moved temp), 301 moved permanently, 404 not found, 401 unauthorized, 403 forbidden, 429 too many requests, 500 server error, 502 bad gateway.
  - HTTPS:
    - Security layer of TLS/SSL to encrypt communications.
    - Things can still be altered so have validation mechanisms.
- RESTful API:
  - Model is that clients are performing simple operations against resources.
  - Think about resources and operations in terms of HTTP.
  - Not the most performant solution for very throughput services, JSON is not the most efficient way to serialize and deserialize data.
    - Default for interviews.
- GraphQL:
  - Solve underfetching, where multiple requests and round trips needed to get data, adding overhead and latency.
    - Overfetching:
      - Way too much information, APIs take a while to load and return a lot of data.
  - We specify what fields and nested objects are required.
  - Why use GraphQL?
    - The front-end team needs to iterate quickly and adjust.
    - Complex clients where multiple teams make wide queries to overlapping data.
- gRPC:
  - Remote Procedure Call: uses HTTP/2 and protocol buffers
  - Protocol buffers: a more optimized JSON, binary encoding.
  - Definitions are compiled into client and server stubs.
    - Essentially, binary protocol that’s faster and more efficient than JSON over HTTP
  - Use GRPC when doing internal service-to-service communication where critical performance or when latencies are dominated by the network instead of the work server does.
    - Have public APIs use REST and internal ones use gRPC
- Server-Sent Events:
  - HTTP spec that allows a server to push many messages to client over a single HTTP connection.
  - Allows for server to push many messages as chunks in a single response from the server.
  - Each line is a separate message from the server, client can process each message as it comes in (one big HTTP response, but comes in smaller chunks)
    - Expected that each line is individually processed.
  - SSE connection can’t be open for too long (since server can close down connection).
    - Defines an EventSource object (once closed, automatically reconnects with the ID of the last message received).
    - Servers need to keep track of priors missed from the client while it was disconnected and resend them.
  - Useful for real time updates, notifications as soon as events happen (great option for keep bidders up-to-date on current price of auction).
- Websockets:
  - Persistent TCP style connection, real-time bidirectional communication with broad support.
  - WebSockets enable servers to push to clients without being prompted by a new request.
    - Clients can also push back without a wait.
  - Initiated with a HTTP upgrade protocol, TCP connection to change L7 protocols.
  - How it works?
    - Client initiates websocket handshake over HTTP (backing TCP)
    - Connection upgrades to Websocket, websocket takes over TCP connection
    - Client and server send binary messages to each other.
    - Connection stays open until explicitly closed.
  - Need to define how client and server are exchanging info (serialized json messages).
  - Useful in high-frequency, persistent, bi-directional communication situations.
- WebRTC:
  - Peer to Peer communication between browsers without an intermediary server.
  - Good for video/audio calling and conferencing applications, as well as document editors.
  - Uses UDP.
  - More complex than client-server models because most clients don’t allow inbound connections for security reasons.
  - Central signalling server, keeps track of which peers are available together, with their connection info.
    - Once client has connection info for another peer, they can establish direct connection without intermediary servers.
  - Challenges: most clients don’t allow inbound connections for security reasons, and majority of users are behind NAT device.
    - Work around: STUN: session traversal utilities for NAT, allow for connections to be made to publicly routable addresses and ports.
    - TURN: traversal using relays around NAT, bound requests through central server, can be routed to appropriate peer.
  - 4 steps:
    - Connect to central signalling server to learn about peers
    - Reach out to a STUN server to get public IP address and port
    - Share this info with each other through signalling server
    - Establish a peer-to-peer connection and start sending data
      - Fall back: turn server
  - Useful for audio/video calling and conferencing applications.
  - Also useful for document editors to scale to many clients (but not necessary).
- Load Balancing:
  - Horizontal scaling: add more machines.
  - Client-side load balancing:
    - Client itself decides which server to talk to, involves making a request to a service registry or directory which contains a list of available servers.
    - Then make a request to that server directly.
    - Example:
      - Redis: gossip protocol to share information about the cluster (where nodes are present, status, every node knows about every other).
        - To connect, client requests any of the nodes, asks them about the nodes participating + shards of data.
        - To read or write, client hashes key to determine which shard to send request to, then uses locally retrieved node info to decide.
  - DNS:
    - Resolver returns a rotated list of IP addresses for the domain.
    - Each new request gets a different ordering of IP addresses or different sets.
    - Each client gets a different ordering, so we hit different servers.
- Dedicated load balancer:
  - Software that sits between client and back end servers and makes decision about which server to send the request to.
    - If we don’t want the client to know other servers exist or have a large number of clients.
  - Layer 4:
    - Operate at the transport (TCP/UDP) layer, making decisions based on network information like IP addresses and ports without looking at the actual content of the packets.
      - Assume we have TCP connections directly between client and server.
      - Maintain persistent TCP connections, fast and efficient due to minimal packet inspection, can’t make routing decisions based on application data, useful when raw performance is the priority.
      - When client establishes TCP connection through L4 LB, same server handles all subsequent requests.
      - Best when we need persistent connections or high-performance applications.
  - Layer 7:
    - Operate at the application layer, can look at the content of a request and make intelligent routing decisions.
      - Look at a request and forward to the appropriate back end server.
      - Can:
        - Terminate incoming connections and make new ones.
        - Route based on content.
        - More CPU intensive.
        - More flexibility and features.
        - Better suited for HTTP based traffic.
      - The underlying TCP connection isn’t relevant.
  - LBs use health checks: essentially determine whether a server is healthy or not.
    - Ping server and see whether request is a 200 success.
  - How to distribute requests?
    - Round robins: distribute sequentially
    - Random: distribute randomly across servers
    - Least connections: go to the server with the fewest active connections
    - Least response time: request go to the server with the fastest response time
    - Use a IP Hash: client IP determines which server gets the request (useful for session persistence).
- Most cases, round robin or random is good.
  - For services requiring persistent connections, least connections is good, avoid situation where a single server gets all active connections.
- Emphasize data locality (query closest to data).
  - CDNs: servers that host static content closer to the user.
    - Must be very cacheable data.
  - Regional partitioning: if a lot of users in a single region, partition data by region so that each region only has data relevant to it.
- How to handle failures?
  - Timeout if request doesn’t happen, then retry.
  - If slow, retry request and likely succeed (which is why idempotent APIs are best because we can retry multiple times without causing issues).
  - Back off: retry, wait a short amount, retry, wait a longer amount.
    - Allow system to recover.
    - Retry with exponential backoff (add jitter) so that all failing requests don’t synchronize and a retry causes all of them to fail.
- Idempotency: APIs can get called multiple times and they produce the same result.
  - HTTP get requests, don’t change the state of system.
  - Use an idempotency key: ID for a request to ensure the same request is idempotent.
    - Server side, we see whether we’ve processed a request with the key, and if not, process it.
- Thundering herd:
  - Database down, we need to reboot, we get a firehose of retries and angry users.
- Circuit breakers:
  - Monitor for failures, if they exceed a threshold, requests immediately fail without attempting actual call, then half-open state, test request seeds whether to close circuit or keep open.
  - Benefits: we fail fast, reduce our load, self-heal, improve UI, and prevent cascading failures.
  - Useful when doing reliability, failure modes, or disaster recovery.
  - Do when:
    - External API calls to third party services, database connections + queries, service to service communication, resource intensive operations, any call that could be slow.
