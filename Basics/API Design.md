  - Three choices:
    - Use REST to manipulate resources identified by URLs.
    - GraphQL: query exactly what’s needed
    - RPC (remote procedure call), communication between microservices.
  - Resource modeling: just key entities in design.
  - REST resources should be things, plural nouns.
  - How to handle relationships?
    - Nest resources when there’s a clear parent-child relationship and when the relationship is required (one value is required for the other).
    - /events/{id}/tickets
    - Use query parameters when the filter is optional.
- Use HTTP methods:
  - GET: retrieve data without changing anything.
  - POST: create new resources, server assigns ID and returns new booking.
    - Not safe or idempotent, calling it multiple times results in multiple bookings.
  - PUT:
    - Replace an entire resource or creates it if it doesn’t exist.
    - Idempotent: sending data multiple times results in final same state.
  - PATCH: update part of a resource, not guaranteed to be idempotent.
    - Result depends on how you implement it.
  - Delete: removes a resource:
    - Idempotent because we leave the server in the same state
  - Get, put, delete: idempotent because calling them multiple times doesn’t change final result.
  - POST and PATCH: not guaranteed to be idempotent.
- Ways to pass data:
  - Path parameters: identify which specific resource we are working with.
  - Use path parameters when value is required to identify the resource, without it, request doesn’t make sense.
  - Query parameters: filter, sort, modify how resources are retrieved,
    - All optional
    - Work well for pagination.
  - Request body:
    - Actual data that’s getting sent to create or update resources.
    - Complex data structures that might be too large for a URL.
- Returning data:
  - Status code: indicates whether request was successful or not.
  - Response body: data that we want to return to the client (JSON)
  - Client errors: 400s (404 not found, 401 auth required, 400 bad requests).
  - Server errors: 500.
- GraphQL:
  - Avoid overfetching unnecessary data or underfetching (use too many requests).
  - The query includes exact fields we want returned.
  - Need to implement query parsing, schema validation, caching strategies.
  - REST is simpler and more straightforward.
  - Need to design a schema that defines data types and relationships
    - Results in the N + 1 problem where we do one query and then N queries for specifics, whereas a single query/join would be quicker.
    - Handle authorization differently, secure individual fields not endpoints.
- RPC:
  - Communication paradigm allows client to call a procedure on a server and wait for response.
    - Uses binary serialization and HTTP/2, so quicker than JSON.
  - Use protocol buffers to define service contracts, essentially what methods and data structures are used and get returned.
  - Useful when:
    - Performance is critical, type safety matters, focusing on service-to-service communication, streaming is needed.
- Pagination:
  - When dealing with large datasets, can’t return everything at once.
  - Break up data in manageable chunks.
  - Offset-based:
    - Specify how many records to skip and how many to return:
    - /events?offset=20&limit=10, we get records 21-30.
    - Problems with large datasets where if someone adds new event while we are paginating through results, we might miss duplicates or records as data shifts.
  - Cursor-based:
    - Use a pointer to a specific record instead of counting from the beginning.
    - Cursor pointing to the last record:
      - { "events": [...], "next_cursor": "cmd9atj3p000007ky19w1dpy2"}
    - Then used in the next request:
      - /events?cursor=cmd9atj3p000007ky19w1dpy2&limit=10
- Versioning:
  - Need to tell clients what version of an API is getting used.
  - URL versioning: version number is in the path
  - Header versioning: put the version in a header, keeps URLs cleaner and follows standards better but less obvious to devs and harder to test.
- Authentication vs authorization:
  - Authentication: verifies identity
  - Authorization: verifies permissions
- API Keys:
  - Long randomly generated strings that act as passwords for applications.
  - When a client makes a request, include the API key in the authorization header and the server looks up the key to identify who is making the request.
  - Ideal for server to server communication where both sides are controlled.
  - When the booking service calls a payment service, the API key is straightforward and effective.
    - Also good for programmatic access.
    - Not the right choice when building user-facing products.
    - Users shouldn’t be managing long crypto strings, and API keys don’t expire or carry user context.
- JWT:
  - Encode information in the token itself.
  - When logged in, the server creates a JWT containing user ID, permissions, and expiration time.
    - Sign token with secret key.
  - When that token comes back with future requests, you can verify through checking the signature and can read information directly from the token.
  - JWTs work well for distributed systems because token validation can happen independently since it’s stateless.
  - Use API keys for internal service communication and external developer access.
    - Use JWTs for user sessions.
    - They are stateless and can carry user context, so ideal for user facing applications.
- RBAC:
  - Specify roles to users and permissions to roles.
  - In API, check both authentication and authorization.
    - For an operation, check whether the user is authenticated.
    - For an operation, see whether user is authorized, has perms to do this.
- Rate limit:
  - Restrict how many requests a client makes over a given time.
  - Per-user limits, per-ip limits, endpoint-specific limits.
  - Implemented at API gateway level or using middleware.
  - When exceeded, we return a 429 too many requests status.
