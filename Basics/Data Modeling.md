- Data Modeling:
  - Defining application’s data is stored and structured and related.
  - Deciding what entities exist.
  - Most of the time, we use relational databases.
    - Enforce relationships through foreign keys and have ACID guarantees.
  - Good at handling complex queries, but be suspicious of multi-table joins because they can be performance traps.
  - Strong consistency being a non-functional requirement: SQL’s acid guarantee ensures this.
- Document DBs:
  - JSON documents with flexible schemas, good for rapidly evolving applications where data fields upfront.
  - Data modeling is nested and embedded.
  - Consider over SQL when schema changes frequently, data is deeply nested.
  - Data modeling: denormalize aggressively, embed related data within documents, trade storage space and update complexity for read performance.
    - This is because lookups are expensive going through an entire user’s document.
- Key value stores: just think a dictionary.
  - Good for caching, session storage, feature flags where we need data up a single identifier.
    - Used with SQL (SQL truth, redis key-value cache in front for hot data).
  - Schema becomes flat, we denormalize heavily and duplicate data to support different patterns of access (since no joins or queries), so good for reads but bad for consistency.
- Wide column databases:
  - Data is column families where rows have different sets of columns.
  - Optimized for write-heavy workloads or time-series data.
  - For posts, row is a key, we have a column family of posts where we have timestamp and the actual post.
    - Useful when enormous write volumes, time-series data or analytics workloads.
    - Telemetry, event logging, IoT sensor data.
  - Duplicate data across multiple column families for access patterns.
- Graph databases:
  - Data is nodes (entities) and edges between entities.
  - Never use in interviews.
    - Facebook models its graph with SQL.
- How to design schema?
  - Data volume: where data can live.
    - If user data and post data are on separate systems, need distinct schemas with how they refer to each other.
  - Access patterns:
    - How is data queried?
    - What should be denormalized or indexed?
  - Consistency Requirements:
    - How tightly coupled data can be.
    - Strong consistency for finance, so keep data in the same DB with acid guarantees.
- Primary keys: identify individual keys.
  - Foreign key: another primary key.
- Relationships:
  - One to many: a user has many posts, a post has many comments.
  - Many to many: users like many posts, posts are liked by many users.
  - Enforced by foreign keys, ensure referential integrity.
    - Sometimes completely dropped due to insertion validation and taken care of application logic wise.
- Add constraints: NOT NULL, UNIQUE, CHECK, ensure that data quality is correct (thought we add write overhead)
- Indices:
  - Do queries really quickly, data structures that allow data bases to find records quickly without scanning every row.
  - Index on id to find all posts by a user for example.
  - Connect indices with API endpoints.
- Normalization:
  - We only store each piece of information in one place.
  - Data is not duplicated across tables, preventing anomalies where updates happen at one place, not another.
- Denormalization:
  - Data is duplicated across tables to prevent expensive joins.
  - However, this can lead to inconsistent state when an update happens and not all data gets updated.
  - Start with clean normalized, denormalized when needed.
  - When necessary:
    - Analytics reporting system (aggregating infrequent data changes)
    - Event logs and audit trails (capturing a snapshot of data)
    - Heavily read-optimized systems (search engines where consistency is less critical than speed)
  - Alternatives: put a cache in front of denormalized representation of data.
- Sharding:
  - When data is too large for one db, across multiple machines.
  - Shard by the primary access pattern: if we are querying mostly by user, shard by user_id.
    - We want to avoid joins across shards.
  - Avoid cross shard queries, essentially merge results (expensive and complex)
  - Don’t shard by time-range: all current writes hit the same shard (creating a hot shard), result in uneven distribution of requests in write-heavy systems.
    - Works better in archival, analytics workloads.
